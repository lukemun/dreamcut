# performance-review — evolution log

## Purpose
Make slow DreamCut paths (playback start, Replay, polled editor reads, renders and background preparation) measurably faster without changing their output. Scope: measured diagnosis and behaviour-preserving fixes; correctness defects go to code-review and layout to editor-ui-design. Good looks like: a symptom stated as a number on a recorded machine state, costs expressed in the path's own sizes, fixes in impact order, and the same measurement repeated before → after.

## 2026-10-24 — repository-wide review entry point

- **Observation:** A whole-codebase architecture and time/space complexity review may start without a known slow symptom; the existing procedure assumed one.
- **Change:** Added subsystem coverage, representative workload selection, separate runtime/memory/storage analysis, architecture ownership checks, and evidence-ranked findings. Retained measured before/after verification and preservation of output.
- **Verification:** Routing walkthrough: a broad performance audit starts with inventory and workloads; a specific slow poll retains the measurement-first path; a correctness-only review routes to code-review. This instruction change alone establishes no runtime speed improvement.

## 2026-10-24 — reusable playback and polling lessons

- **Observation:** Startup buffering, repeated polling projections, manifest reads and background preparation can compound; an idle interval in a benchmark can itself trigger competing work.
- **Change:** Document measuring foreground and background ownership together, reusing unchanged projections, bounding startup work and checking cache keys before expensive preparation.
- **Verification:** Preserve workload-specific receipts outside distributed documentation. Unit coverage for startup bounds, poll invalidation and control round trips provides regression evidence; fresh workload measurements are required for performance claims.

## 2026-10-24 — second tier: unmix footprint, validation and fingerprint caches, scene identity

- **Change:**
  - The split template skips the other two passes when a piece draws nothing in a frame, and reads back and unmixes only the piece's bounding box. Its passes still draw the full frame, because a frosted pane blurs its surroundings.
  - Pending-card validation is cached by the card plus a project key that leaves out proposals, memory and history, and the proposal list is read once.
  - Prepared-preview identities are cached per input object and not computed while disabled.
  - The GPU replay-profile key digests the scene key instead of re-embedding it.
  - Per-frame diagnostics nothing samples per frame refresh at 4 Hz while playing.
  - HyperFrames source fingerprints are reused while every file's size, mtime, ctime and inode are unchanged.
- **Verification:**
  - Stacked Glass layers still match the whole graphic exactly (0 pixels off at 7 moments).
  - Per-frame cost of a piece composition: chart stat 36.7 → 24.8 ms, orbit dot 23.4 → 15.6 ms, title card 45.7 → 34.0 ms.
  - A poll after one card changes: 0.34–0.42 s → about 0.10 s. After any project change: about 0.16 s.
  - New tests cover fingerprint invalidation on a size- and mtime-preserving rewrite.

## 2026-10-24 — cache-capacity and request-snapshot checks

- **Observation:** Entry-limited LRU caching can thrash on full ordered scans just above capacity. Repeated scans inside one request also duplicate metadata and path work.
- **Change:** Require cache workloads above entry and byte budgets, with invalidation and caller-isolation checks. Prefer a complete request-local snapshot when repeated readers need the same inventory; retain fresh validity checks on source files.
- **Verification:** Episode-summary regression tests cover reuse at 129 entries with a 128-entry cap and partial reuse above the byte budget. Media-binding tests cover complete snapshot reuse, changed-file invalidation and fresh discovery. Local benchmark receipts hold machine-specific timings.

## 2026-10-25 — the dev server is not the product, and server stalls differ from browser waits

- **Observation:** "Preview took too long to load" and editor freezes appeared with several agent sessions open. Connection starvation and unread response bodies were suspected first; direct tests ruled both out. A trivial request took 14.6 s from curl, so the server itself was stalled. In `next dev`, each request to a dynamic route starts and discards a Node process (static-paths check), and source edits trigger recompiles. A preview request's fixed 15 s timeout also counted time queued and time the pane was hidden.
- **Change:** Measure server timings on a production build; time the same URL with curl and in a tab to separate server stalls from browser waits; budget request timeouts on visible time only. Proposal previews now spend their budget only while the page is visible and log queued, server, waiting and reading time; both preview routes return `Server-Timing`.
- **Verification:** Same machine and load (load average about 25, other work running), 4 editor tabs, 30 s, one probe request: `next dev` p50 70 ms, p95 194 ms, server CPU median 100%, 127 Node processes started; the production service p50 10 ms, p95 27 ms, CPU median 18%, none started. Unit tests cover the visible-time budget and the phase line; a delayed preview in a real Chrome tab logged its phases.

## 2026-10-25 — a whole-timeline index rebuilt per caption

- **Observation:** Previewing 14 selected cards on a 9½-minute talk with 1,215 one-word captions took 60–124 s and hit the editor's 15 s budget; one card alone took about 1 s. A CPU profile of the derive step put almost all the time in `changedSince`: the proposal derive called `changedSince(timeline.elements)(element)` inside the per-caption predicate, so it JSON-stringified every element once per caption, about 5 s for each card derived after the caption card.
- **Change:** Build the changed-element check and the touched-id set once per derive (`timeline-editor-agent-apply.ts`). Preview, batch preview, approval and batch apply share the path. The skill lists per-item indexes of the whole collection as a waste shape.
- **Verification:** Derive per card after the caption card: about 5 s → about 30 ms (Node, same machine). Batch preview of the 14 cards over HTTP: 60–124 s → 4.3 s, measured on `next dev` with other sessions running, not on a production build. `proposal-derive-scale.test.ts` derives a card on a 1,500-caption timeline under 1.5 s; it fails on the old code (2.5 s).

## 2026-10-25 — edit chapters rebuilt from every snapshot on each edit

- **Observation:** The proposals inbox poll (`include=pending_details`) took 21–30 s of CPU cold on a 9½-minute talk with 129 history snapshots (1.9 GB). The profile put about 80% under `memoryEvents → editChapters`: it parsed every snapshot and sha256-hashed two serialisations of every clip per consecutive pair. Its cache key covered all history files, so each new snapshot (every edit) repeated the whole scan.
- **Change:** `editChapters` keeps per-snapshot results keyed by stat and by the readable predecessor they were diffed against; a rebuild re-reads only new or rewritten snapshots and the successor of a changed or removed one. Each clip is serialised once per snapshot and compared as a string, with no hash. Labels are still recomputed on every rebuild.
- **Verification:** On a clone of that project (load 26–35): `editChapters` cold 26.9 → 16.3 s CPU, after one appended snapshot 26.9 s → 0.37 s, and output byte-identical to the old full rescan. Route cold CPU 30.4 → 22.3 s under higher load; JSON parsing (about 11 s) is now most of it. `editing-chapters.test.ts` checks output against the old implementation through append, rewrite, removal and unreadable snapshots, and that an append costs under a fifth of a cold build.

## 2026-10-25 — preview proxies re-probed after every server restart

- **Observation:** The first timeline read in a server process spent 0.7–1.9 s waiting on `ffprobe`, one synchronous probe per preview proxy (`validatePreviewProxy`). An in-process cache keyed by stat already shared one probe between the preview-quality and hydration paths within a process, but it was empty after every restart or rebuild. The proposal preview route also spends about 1 s cold in `ensurePreviewAudioClock`; that is a profiling-clone artefact, because the audio clock's file name hashes the treated file's absolute path.
- **Change:** Successful probes are saved in `preprocess/preview-proxy-probes.json`, keyed by a hash of the proxy's media path plus its size, nanosecond mtime and the probe's version. Failed probes are not saved. Hashing the path keeps the cache from counting as a media reference that would keep a retired proxy on disk (`retireSupersededPreparation`).
- **Verification:** `profile:route` on clones that already have saved probes (the restart case), load 25–33: `week-recap` timeline cold 2.95 s → 0.56–0.67 s, `times-square-3d-flyin` 0.97 s → 53–65 ms, `proposal-preview` 2.12 s → 1.65–1.79 s. No probe stacks under `--stacks spawn` except proxies made after the clone. Tests cover a cache hit after restart, re-probing on a changed size or mtime, and failed or older-version probes.

## 2026-10-25 — spatial assessment re-measured each shape and re-sorted the timeline per call

- **Observation:** `assessProjectSpatial` runs on every proposal preview. On a 20-piece hand-drawn sketch project it cost about 330–640 ms CPU warm, mostly `normalizeShapeContours` and `contourLength`: each pair and each sampled time resolved the shape's props and re-measured its whole outline, although only draw-on, rotation and scale change over time. - **Verification:** Pre-change copies of the five files and the new code run on the same inputs in one process, alternated, load 23–47: output JSON byte-identical (snapshot id included) on the three projects, scoped and unscoped, and on a card preview; warm CPU median sketch 328–507 → 51–72 ms, captions 465–602 → 345–459 ms, card preview assessment 47–58 → 38–46 ms. ## 2026-10-25 — hardware-decoded alpha video read back on every frame

- **Observation:** GPU playback of a project with three transparent VP9 layers spent about 30 ms of GPU-process time per frame, the largest share in `DoReadbackARGBImagePixelsINTERNAL`, while up to twelve worker threads waited in `CommandBufferProxyImpl::WaitForGetOffset`. The trace's worker URLs named them: blob workers started by the demuxer's colour/alpha merger. It merges side-data alpha on the CPU for every decoded frame, and hardware frames live on the GPU, so each merge read colour and alpha back synchronously (about 3.5 readbacks per frame, 135 merges a second). The hardware decoder also returned opaque alpha as 254.
- **Change:** `BrowserFrameProvider` asks for software decoding (`prefer-software`) for transparent tracks only. libvpx frames are already in memory, so the merge copies instead of reading back. Opaque sources keep the hardware decoder.
- **Verification:** Playback benchmark on `pnpm dev`, 5 s trace, alternated, load 13–31: GPU-process time per frame 27.4 and 29.0 → 10.0 and 10.2 ms, readback 2.3–2.7 s → none, worker waits about 5 s per thread → none, GPU frame p95 39.9 and 25.8 → 11.8 and 10.2 ms. Decoded I420A frames from all five of the project's alpha proxies (60 frames each) are byte-identical to ffmpeg's libvpx `yuva420p`. Hardware decoding matched in colour but differed by 1 in alpha. Stalls of 0.3–0.9 s remained in both cases; they are not caused by the readback.

## 2026-10-25 — GPU preview start timed out waiting for the worker script

- **Observation:** On a 9½-minute project with about 8,000 elements, GPU preview in headless Chrome on `pnpm dev` fell back with "GPU preview initialization timed out" in 2 of 5 cold loads (load 23–43). The 30 s limit ran from mounting the canvas. The worker's own start (CanvasKit script and wasm, compositor, runtime over every element) took 1–5 s. The worker script request took 15–24 s, although the server answered it in 0.3–7 s and esbuild builds the bundle in under 0.1 s. The request was waiting behind the page's slow API requests (proposal details 4.7 s alone, batch preview, audition compile and a backlog of 5 s polls, each taking 15–30 s in the page) and the browser's six connections per host. Element count matters through that server and page load, not through GPU start. At load 7–10 the same start took 5–6 s.
- **Change:** `GpuPlaybackComposition` gives each start phase its own 30 s: loading the worker script ("GPU preview worker did not load in time.") and, from the worker's boot message (`GpuWorkerClient.booted`), CanvasKit and device start (the existing message). Device versus project failure classification is unchanged.
- **Verification:** With the worker held back 22 s and its init 12 s inside the page (no request interception, which breaks worker media fetches), the start finished 34.6 s after mount and frame 0 was drawn; the old single limit would have failed at 30 s. With the script held back more than 30 s, the new load limit fell back as before. `week-recap` gpu benchmark completed on CanvasKit at load 8 (first motion 3.6 s). Not checked: the creator's stable build under load, and why the effect starts the worker four times while the player measures its size.

## 2026-10-25 — preview audio clock re-rendered after every project move

- **Observation:** A cold proposal preview of a voice-enhanced card took 1.68 s wall, 0.44 s CPU (load 9–11). The `--stacks spawnSync` profile put 751 ms under `ensurePreviewAudioClock`, which every timeline and preview read reaches through `hydrateLegacyTreatedPreviewAudio`; FFmpeg ran only on a miss, but its output name hashed the treated file's absolute path, so a moved projects folder, a Library move or a profiling clone always missed. Treatment outputs (`outputLocation` for noise reduction, voice enhancement, loudness, detach, reverse) still hash the absolute path; their cache hits also re-run analysis (`findQuietestNoiseWindow`, loudness measurement) on every call. ## 2026-10-25 — GPU preview started its worker once per settling player size

- **Observation:** Opening `week-recap` (about 8,000 elements) in GPU preview constructed four GPU workers and terminated three; `times-square-3d-flyin` constructed two. A temporary log in the start effect showed every restart came from `display`: the player measured 508×286, 748×421, 1022×575 and 891×501 within about 200 ms of mount, and each delivery size was a dependency of the effect that starts the worker. The superseded workers were terminated before their boot message, so the waste was three extra worker-script requests and builds competing with the page's requests, not three CanvasKit starts. The replay-profile key uses the session key, so stored hints miss once.
- **Verification:** Scratch Playwright count on `pnpm dev`, two runs each, load 7–16: worker starts `week-recap` 4 → 1, `times-square-3d-flyin` 2 → 1, none terminated; after a viewport change both sent two `resize` messages, no new worker, and redrew the paused frame (pixels checked). The `week-recap` gpu benchmark completed at load 18–34 (ready 16–17 s, first motion 1.6–7.5 s). ## 2026-10-25 — proposal refresh re-read the whole timeline for every card
